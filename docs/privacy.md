# Privacy baseline

Va de Vi is private by default. The repository contains no analytics, production identifiers, or personal fixtures. Public/default configuration uses `AI_PROVIDER=none` and `RESEARCH_PROVIDER=none`, so Vicenç’s deterministic tools and ordinary application flows make no external AI or research call. Local provider state, environment files, build output, and temporary data are ignored by Git. Checked-in runtime configuration contains synthetic placeholders only.

A private deployment may opt into fixed-host public-data research with an identifying user agent. It may separately configure Workers AI with a binding and allowlisted model name. In that mode the provider receives the current bounded question plus authorized structured statement summaries, which may include an aggregate personal sample; it does not receive saved chat history, raw repository rows, credentials, hidden authorization context, or arbitrary page content. Provider-specific privacy review is required before enabling either optional path.

Wine and tasting data is scoped to a Space and can be read only after active-membership verification. Optional label photos are resized, re-encoded, stripped of metadata in the browser, and then validated again by the Worker. R2 objects are private: authenticated routes perform membership checks, and opaque object keys are neither authorization credentials nor normal client-contract fields.

Offline storage is intentionally limited to the last verified session bootstrap, Wine Memory/session/cellar/wishlist/price snapshots, drafts, queued mutations, conflicts, and temporary processed photo blobs. It is partitioned by user and Space, never contains manually persisted bearer tokens or raw audio, and can be cleared explicitly. Cellar, wishlist, and stored-price snapshots are read-only offline; current lookup and writes require an authenticated online request. Logout or account switching clears the outgoing user's data. On the next successful bootstrap, data for removed Spaces is purged.

Vicenç action drafts are private review objects, not saved chat history. A pending draft is bound to one user and Space and retains its validated payload and review summary for no more than 30 minutes. Confirmation, cancellation, or expiry removes both content fields; only its action type, payload hash, terminal timestamp, and optional confirmed resource reference remain for replay safety and audit. A scheduled cleanup enforces expiry without requiring another user request. A canceled or expired draft cannot mutate application data.

Incomplete media reservations expire after 24 hours and are not treated as durable user media.

Phase 6 implements export and deletion. Export produces a versioned JSON document plus selected CSV datasets for the authorized scope: an owner or admin exports the Space, a member exports their own contributions plus shared wine metadata they can already read, and another member's unsubmitted draft note is withheld in every scope. Photo bytes never leave implicitly — the JSON lists each asset as requiring selection, and a ZIP is produced only for an explicit, authorized selection. Exported CSV cells that begin with a spreadsheet formula character are quoted so exported user text is never evaluated.

Deletion is confirmed, recoverable, and idempotent. A Space owner types the Space name to schedule deletion; an account deletion requires a sign-in within the last 15 minutes. Both create a job with a recoverable grace period — seven days for a Space, 24 hours for an account, pending the §23 privacy review — and at most one job stays open per target, so repeating a confirmation never schedules a second purge. A scheduled handler purges active D1 rows and the matching R2 objects independently of any later request, and re-running it changes nothing. Leaving a shared Space removes access without deleting shared records, and pseudonymizes authorship only on request. Provider-managed backup and time-travel retention follows its own schedule and is described as such rather than as immediate physical erasure.

The usage and budget report contains aggregate counters only: daily counts per capability, the application caps, and the configured provider modes. It stores and returns no wine name, note text, chat text, email address, location, or provider payload. Reaching a cap degrades the affected capability to its deterministic or manual path; it never upgrades a plan or switches to a paid model.
